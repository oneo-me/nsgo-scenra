# Scenra architecture

Scenra is a single-window [NSGo](https://github.com/nsgo-dev/nsgo) desktop app, for desktops only, built from `scenraview`, which gives other NSGo apps the same support for Scenra files, as Agio's `chatview` does for conversations. Its title bar holds tabs, as Figma's does: a home page always first, of the folders opened lately, then a tab per open folder, each an editor of its own, and at its end the button opening the settings, a dialog over whichever tab shows. An editor works in one folder, whose Scenra files the sidebar lists in the groups their names give them; each file holds designs of screens, one component designs share or flow charts, never two kinds. One file at a time shows as the document, with its undo history, under a header naming it, beside the assistant running the window's height, whose conversations, one shown at a time and chosen in its header, are about the folder. The design and diagram draw it.

## Code map

| Path | Responsibility |
| --- | --- |
| `flowfile/` | The Scenra file format: a design's elements or a flow's nodes and edges, parsing, canonical formatting and edits. Its package comment is the format's reference. |
| `scenraview/` | The `Editor` an app opens a folder of Scenra files in, and its views: `Window`, or the `Header`, `Sidebar`, `Workspace` and `Assistant` it lays out. |
| `scenraview/editor.go`, `folder.go`, `header.go`, `diagram.go` | The open folder and the files found in it, the document shown and its history, the header naming it, and the flow chart. |
| `scenraview/sidebar.go`, `mockup.go`, `icons.go`, `comments.go` | The list of the folder's Flows and Views groups and grouped designs, the drawing and playing of a design, and the comments and notes on its elements. |
| `scenraview/showcase.go`, `gitdiff.go`, `cover.go` | The folder's components drawn together, the lines Git says its files changed, and a project drawn small. |
| `scenraview/outlet.go`, `layout.go` | The designs filling others' outlets, and the folder's designs laid out unseen for agents. |
| `scenraview/assistant.go`, `files.go` | The folder's conversations, run by an Agio backend and kept to resume, and the files read again as agents write them. |
| `scenraview/server.go`, `selection.go`, `check.go` | The MCP server telling agents what the user sees of a file, and the problems of a project's files told without an editor. |
| `scenraview/locales/` | The views' messages, which an app's catalogs may supply other languages of. |
| `cmd/scenra/` | Scenra, the app: the window, its tabs and home page of recent folders, menu, the agents it runs and their settings, the model titling conversations, opt-out usage statistics, a demo build of a scripted conversation for the website's screenshots, `nsgo.yaml`, assets and its own `locales/`. |
| `cmd/scenra/resources/skills/scenra/` | The skill teaching agents the format and the NSGo components designs become, wherever the files are edited, which ships among the app's resources. |
| `cmd/scenra/resources/skills/scenra-app/` | The skill teaching agents in the app to ask its server, naming their tab, what the user sees and what their files got wrong. |
| `website/` | The official static site, in English and Simplified Chinese, deployed to GitHub Pages. |

## Boundaries

- `flowfile` never imports NSGo, so the format stays testable on its own.
- The assistant is a coding agent run through [Agio](https://github.com/oneo-me/nsgo-agio), not a model client of Scenra's own, so it brings the user's accounts and can read the project. Agents edit the file with their own tools, as the skill teaches, rather than through drawing tools: plain text is what they edit best. Only titling a new conversation asks a model directly, an OpenAI-compatible one the user sets, through Agio's `naming`, as a title needs no agent. What they cannot see, the selection, the open screen and flow, the comments and the file's problems, the editor's `Server` tells them over MCP.
- `scenraview` is product-neutral: the host app gives it the Agio backend, the server and skill its agents get, where to set them up, its toaster and the storage prefix that reopens files, and keeps menus, settings, statistics and the window to itself; it hears right clicks on elements and nodes for the host to open menus of its own, as Scenra has none there. It ships no app catalog, so it never sets the app's languages.
- A file holds designs or flows, never both, so a project is a folder the agent grows file by file, and screens or flows seen together, such as a screen's states, share a file. Each starts with its own line and, once there are several, has an ID taps, the selection and the server name it by; keys of elements and nodes put its index before their paths and IDs. The first line may give the file a name the sidebar, header and window show instead, so the agent can title files in the user's language while their paths, which taps, `in=` and uses rely on, stay short, and a gap the editor packs the file's designs or flows apart by, which the agent sets to suit their sizes.
- A project is flat: the windows and screens the app opens are designs at the folder's top, its views, the designs filling their outlets, files of `views/`, its flows files of `flows/` and its components files of `components/`, so a file's name alone names it in taps, `in=` and uses, and moving it between folders breaks nothing. Each kind has one place, so the top lists only what the app opens, which plays the views inside it, rather than mixing them with the pages they show; the first design's `in=` says which a file is, and the server tells agents to move it otherwise. A design at the top wins over a view of its name, which the server tells of. Designs and components grow into groups by their names instead, one `/` splitting a group from the name the sidebar and the showcase show, as a name, unlike a path, is the user's language and changes nothing that links to the file; groups do not nest, keeping the list one level deep. Flows and views take no groups by name: each kind shares one group atop the sidebar, under the components, as the few charts a project has are its overview rather than one screen's, and views are reached through their hosts. The scan still finds Scenra files in other folders, which the editor leaves out and the server tells agents to move.
- A component, a piece designs share, is a file of `components/` at the top of the folder, which a design or component draws by its path there with `use`, so every use follows one file and no link needs a path relative to the file using it. Any design, at the top or a view, draws as a component too, by the name taps give it, so a screen embeds another without copying it into `components/`, which holds only the shared pieces the showcase reviews; a component wins over a design of its name. A use is one element of the file using it: what the component holds selects the use and takes no comments there. A use draws as the component's element at its top, given the use's classes after its own, as React passes `className` to a component's root, rather than as a box around it, so a component lays out where it is used as its elements written there would. A use changes its component only through the elements the component names, as Figma's instances do, so a component's author decides what may vary and every other edit still reaches every use; the use's attributes carry the changes, so they stay with it in the file, and a change to a component the use draws inside passes down by names, never by element paths, which shift. Where uses differ by more than values, the component leaves slots the use fills with elements it holds: those stay the using file's, keyed by their paths there and selecting themselves, though a slot lays them out, so an element's frame is kept in the view holding it rather than its parent's. Drawing a component keeps the components around it, which it may not use again, while what a fill holds draws among those around the use, so a card may hold a card but no loop draws forever. The scan keeps the components' elements, so a design redraws as an agent edits one, and the server reports uses of missing components, loops by their chain of uses, and fills of no slot.
- The components show together as a view of the folder rather than a file, in place of rows in the sidebar, as the user reviews them together and the agent edits them: each draws as its own file does, bare on the backdrop it names, as large as its content unless it sets a width, and beside its variants, the states its file declares for uses to pick, and only shows, each group packed close under its name in whatever order and width wastes the least of a landscape pane once each has laid out at its height, and the groups in order, unlike a file's designs, whose order means something. A small one scales up to a least area, an absolute floor or a share of the largest one's, so it stays legible when the whole fits. The document stays open beneath, as the flow pane must, and choosing any file, the one shown too, leaves the view.
- Uses pick a component's variants by ID, applied in order before the use's own changes, so a state is written once in the component and every use picking it follows a change to it. A state set with `state=` applies the component's `selected:`, `hover:` and `group-*:` classes by rewriting them, not by holding NSGo's views in states, which NSGo cannot do for hover or press, so a still drawing, such as a variant beside its component, shows them as a press would.
- A design may fill a box of another design that names itself an outlet, as a window's content area, so the window is drawn once and its screens draw only what changes. It draws alone at the size its outlet lays out at, which the pane learns by laying the chain of hosts out unseen, and plays inside them: what each outlet shows is the pane's state, as the tab shown is, keyed by the outlet's key, so taps inside a design shown there name its own file. A close naming a design the page shows in, or its window, the outermost, closes that layer: an outlet goes back to what it showed, and the design drawn returns through the trail, forgetting what its outlets showed, as a closed window opens afresh.
- Agents cannot see the canvas, and NSGo neither lays out nor captures views outside a window, so the Workspace keeps an unseen layer that lays out the folder's designs and components as the canvas would when the server asks, and the server reports from their frames where elements went and what lays out wrong; without a Workspace it answers without them. `Check` tells hosts without an editor, such as one giving agents a check tool, the server's problems of a folder or one file, and so never how designs lay out.
- The sidebar shows each file's lines changed since the last commit by running the user's Git, so Scenra reads no repository itself; the scan runs it every few seconds, as commits change what it tells without changing the files, never taking locks a Git command of the user's needs, and a folder in no repository, or without Git, shows none.
- A picture a design shows is a file of `assets/` at the top of the folder, named by its path there, so the folder carries its pictures and every image names them alike. The scan reads that folder's pictures, up to a size, and keeps their bytes while their files stay the same, so the editor shows them without loading files from the device, which NSGo refuses, and redraws them as they change.
- A design's words in several languages are catalogs of `locales/` at the top of the folder, named and matched to the interface's language as NSGo's are, so the designs read as the app will and the app takes them as they are. A text names its message by key rather than the catalogs naming elements, so the words follow the text through edits; the scan reads them with the pictures, which every view drawing designs already follows.
- A flow is a workflow of its own, never one screen's: what happens on a screen shows in its design, through taps, outlets and notes, so the user sees a screen's behavior where it is drawn and every flow in one place, rather than some behind a switch beside their screen and others in the Flows group.
- Each tab is an editor made in a scope of its own, so a folder keeps its document, history and conversations while another shows, and closing the tab ends them; a folder opens in one tab, which opening it again shows. Hidden tabs stay laid out, as their canvases and charts must, and only hide. The tabs name the folders, so the editor's Header is left out.
- An editor has one document open, so leaving it, for another file, by closing its tab or the window, saves it instead of asking; undo history goes with it.
- One MCP server serves every tab's agents, so each call names its editor by an ID the conversation's system prompt gives, rather than the server guessing which tab is meant. The ID comes from the folder, so a conversation resumed with its old instructions still names it.
- A recent folder's cover is a design drawn small by `scenraview`'s `Cover`, of the file it showed last or else its first design, so the home page tells projects apart without images of its own to keep.
- The folder is scanned off the UI's goroutine, leaving out hidden folders and `node_modules` and stopping after a limit, so a large folder stays responsive; a file the agent makes in its turn opens.
- Every change to a document goes through the editor, which records it for undo. What an agent writes in one turn undoes together.
- The files are the only channel between the user and the agent, so sending a message saves the user's changes, and the user cannot change the documents while the agent works. A file an agent leaves unparsable keeps the last version that parsed, and the server tells the agent why; one that never parsed shows its error in the workspace, which offers to ask the agent to fix it, and is never saved over.
- The skills are resources, not embedded, so agents read them from the app's package; NSGo names no resource directory, so the app finds them where NSGo's packages put resources. The format's skill names no tool, so it serves agents editing the files anywhere, such as in another app showing them; the app's own skill teaches its server.
- A design is a draft drawn from a few primitives shaped by Tailwind CSS classes, not from ready-made controls, so the agent can draw any look. Classes NSGo does not know reach the agent through the server.
- A design lays out at its size, its device's or the one its line sets so agents can change it, and a flow at the size its diagram's layout takes. The panes compose NSGo's `camera.View`, which pans and zooms them, with their content and tools, since NSGo's zooming scroll views exist only on Apple platforms and NSGo's flow diagram has no camera of its own. A file's designs or flows pack in rows, in order and the file's gap apart, where the whole fits a landscape pane at the largest scale, each under a caption the same size on screen at any zoom.
- Platforms hit-test views without the camera's transform, so the camera hands the pointer on at points of the content and the panes find the element under it from the elements' frames, or the flow whose diagram finds the node. Elements are named by their paths, which the selection and the server use.
- A comment or a note is an attribute of its element in the file, so it is saved with the file and follows the element through edits, where paths shift. A comment asks for a change, which the skill tells agents to remove only once resolved; a note stays, as part of the design.
- A design plays as the app would: a tap opens another design, moving the camera to it in the same file, which a close returns from through the editor's trail of opened designs, or shows a tab's panels in the design tapped. Taps are the press of the design, so its card opens where the pointer rests a while instead, and pressing selects only elements without a tap, or any with Alt. The tab shown is the pane's state, not the file's, and resets when another file shows. A drawn design does not show what plays, so what can be tapped flashes as a design shows or is read again.
- A box whose tap opens the design holding it, or shows the tab shown there, is selected for `selected:` classes, so a component such as a tab bar marks the screen using it without a version per screen. A use's elements are hit-tested by keys joining the use's path and theirs, so their taps play while they still select the use.
- The flow file names icons by their Lucide names, or older ones it maps to them, as `flowfile` cannot import NSGo. `tools/iconsgen`, run by `go generate` after updating NSGo, writes every name NSGo's Lucide package has into `flowfile` and the map from names to icons into `scenraview`.
- The flow pane keeps a diagram for each index of a file's flows, following the document shown instead of remounting per file, and the design covers it while a design shows.
- The chart fits only once a change's batch is over: remounting a chart, or fitting it while it takes new data, trips NSGo's commit check on macOS.
- Files are made only by agents, as the skill teaches where each kind goes and what it holds, so the editor has no way to make one and ⌘N starts a conversation instead.
- A folder's conversations work in it with Agio's full access there, as a design and its flows are made together. Agio persists nothing, so the editor keeps by folder what resumes those whose agents started a session, and opening the folder again resumes them and shows the latest; leaving it, or closing its tab, stops their agents. Editors under the same storage prefix read the kept conversations again before writing them, as each tab keeps its own folder's.
- User-visible words live in `locales/`, in both languages.
- Statistics never carry document content, messages or paths. `nsgo dev` builds and test binaries send none.

## Core flows

**Assistant turn.** Sending a message saves the documents and sends the message to the folder's conversation, whose agent asks the server what the user sees, reads and writes the files and makes new ones. The editor looks at the open files a few times a second and reads a changed one again into its document as a change of the running turn; the server's answer reads them and scans the folder first, so the agent hears of what it just wrote.

**Files.** The app opens a folder, from the picker, the Finder or the command line; opening a file opens its project unless it is in the open one: the folder holding it, or that folder's parent when it is the project's flows, views or components. A folder with no Scenra files where a project keeps them but with a `design/` folder shows that folder's project, as a repository keeps its designs beside its code, while the assistant still works in, and its conversations belong to, the folder opened, so it reads the code it designs. Choosing a file in the sidebar saves the document shown and parses the file in its place. A document saves to the path it was opened from, in the canonical form, so `#` comments in a hand-written file are dropped.

**Statistics.** Release builds send an Umami pageview at start, an event per message sent and heartbeats while the chart or the conversation changes. A queue on its own goroutine posts them and drops failures.

## Data and state

Settings, the language and theme and the naming model's API key among them, the open tabs with the file each shows and the tab shown, the folders opened lately with the file each showed last, each folder's conversations as their agents' sessions, choices and titles, the agent, model and settings chosen last, which new conversations start with, and the install's random statistics ID live in NSGo's storage on the device; the transcripts stay in the agents' own sessions. Documents live only in the folder's files.

## Verification

`go tool nsgo test` drives `scenraview`'s views and the app headless against a scripted Agio driver whose agent writes the file and calls the server, and covers the format and the skill's coverage of it. Real agents need manual review. Check layout and platform behavior by hand with `go tool nsgo dev cmd/scenra`, or with `go tool nsgo test -target macos`.
